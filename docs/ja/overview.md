紹介資料：[英語・トルコ語のアニメーション、英語音声、インフォグラフィック](../../media/README.md)。

**仮称について：** Alice Talkは、暗号技術の例で慣例的に使われる登場人物AliceとBobに着想を得た作業上の仮称です。正式な製品名は今後決定します。この仮称は、他の組織との提携関係を示すものではありません。

**翻訳について：** この文書は翻訳支援を用いて作成しています。[英語の原文](../en/overview.md)を正式な参照文書とします。

**目的：** 助成金、開発者支援、提携の可能性について、初期の検討に用いる資料です。この資料一式は、後日公開する可能性に先立ち、非公開リポジトリで準備しています。

**現状：** 実験的な暗号化メッセージングのプロトタイプを持つ、独立した正式公開前のプロジェクトです。暗号技術の組み合わせについて、独立したセキュリティ監査およびプライバシー監査はまだ完了していません。エージェント層と、より広範なデバイス間の相互運用性は、今後の研究として提案しているものです。

## 1. プロジェクトの目的

Alice Talkは、利用者が自分のアイデンティティ、共有する内容、実行される操作を実質的に管理しながら、複数のデバイスを通じてコミュニケーションを取り、AIアシスタントと協働する方法を探究します。

長期的には、スマートフォン、タブレット、コンピューターを横断する通信層を目指しています。利用者は他の人とメッセージを交換したり、特定の作業にアシスタントを招いたり、あるエージェントが別のエージェントに助けを求めることを許可したりできるようになると考えています。やり取りがデバイスやシステムの間を移動しても、各参加者の鍵に基づくアイデンティティと、各自が委譲した権限が明確に保たれる必要があります。

このプロジェクトは、言語や国を越えたコミュニケーション、より利用しやすいインターフェース、人間の権限を明示した協働という公共的な利益を動機としています。これらは評価すべき設計目標です。世界規模のサービスや、完全に相互運用可能なエージェントネットワークが既に存在することを意味するものではありません。

## 3. 概念上の動作

現在のメッセージングプロトタイプは、エンドポイントでのアイデンティティと内容の処理を、リレーによる配信支援から分離しています。

1. 参加者がデバイス上で暗号学的アイデンティティを作成または復元します。
2. 招待に基づく受け入れによって、実験用メッセージング環境へのアクセスが決まります。
3. 参加者のエンドポイント同士が、暗号化された1対1のセッションを確立します。
4. 送信側のエンドポイントが、リレーによる配信の前にメッセージ本文を暗号化します。
5. 受信側のエンドポイントが、自らが信頼する鍵に照らしてメッセージの真正性を確認し、メッセージを復号します。
6. 明示的に設けられたオフライン経路は、メールボックスの上限内で暗号文を一時的に保持できます。
7. 利用者は暗号化されたローカル履歴を選択できます。ローカルでの保存とリレーによる配信は、それぞれ別の問題です。

```mermaid
flowchart LR
    A["参加者Aのデバイス<br/>ローカルの鍵とメッセージの暗号化"]
    R["リレー<br/>暗号文の転送と上限付きオフラインメールボックス"]
    B["参加者Bのデバイス<br/>ローカルの鍵とメッセージの復号"]
    A -->|"暗号化されたメッセージ本文"| R
    R -->|"暗号化されたメッセージ本文"| B
```

リレーがメッセージを受け付けることと、受信者がそれを読むことは、別の出来事です。通信経路が利用可能であることは、他の人がメッセージを受信したことや読んだことの証明にはなりません。

ライブ送信の経路では、リレーによる受け入れ、明示的なオフライン結果、不確かな結果を区別します。テキストに別のオフライン経路を選ぶのは、明示的なオフライン結果が得られた場合だけです。ライブ送信の結果が不確かでも、自動的に新たなオフライン送信を行いません。これらの規則は曖昧な再試行を抑えるもので、あらゆる状況で厳密に一度だけ配信する保証ではありません。

## 4. 分散化と管理権限

このプロジェクトの分散化という方向性は、アイデンティティと秘密鍵の管理を参加者に委ね、通信に対する単一の管理主体への依存を減らすことを目指しています。

現在のプロトタイプはリレーの支援を受けます。デプロイ環境で管理される参加の受け入れ、接続インフラ、エンドポイントの動作への依存は残っています。信頼の仮定を必要としないことが実証されたネットワーク、グローバルな合意形成、完全に分散化されたガバナンスを提供するものではありません。

レビューに当たっては、この区別が重要です。エンドポイントで管理権限を持つことは、インフラへの依存をすべてなくさなくても有用であり得ます。今後の作業では、どの責任を分散できるのか、どのような前提が残るのか、障害が参加者にどう影響するのかを明らかにする必要があります。

## 5. 暗号技術のアプローチ

プロトタイプは、確立された暗号構成を組み合わせています。その組み合わせの安全性については、独立した評価が引き続き必要です。

| 構成 | 大まかな役割 |
|---|---|
| Ed25519 | 暗号学的アイデンティティの署名。 |
| X3DH方式のプリキー交換を用いるX25519 | 初期セッション鍵の合意。 |
| Double Ratchet | 会話の進行に伴うセッション鍵情報の更新。 |
| XChaCha20-Poly1305 | 保護対象の内容に対する認証付き暗号化。 |
| パスフレーズで暗号化されたローカル保管庫 | 封印された形で保存されているローカルのアイデンティティ情報の保護。 |

この設計は、メッセージの完全性、参加するエンドポイント間の機密性、セッション鍵の更新を支えることを意図しています。こうした意図は、システム全体のエンドツーエンドの安全性、前方秘匿性、侵害後の回復についての形式的な証明ではありません。

暗号学的アイデンティティが示すのは、鍵情報を管理しているということです。送信者が誠実であること、現実世界の身元が確認されていること、要求された操作が許可されていることを示すものではありません。

この概要では、実装コード、パケット形式、鍵導出パラメーター、デプロイ手順、運用の詳細を意図的に省いています。確立された暗号構成の名称を挙げても、プロトタイプが他製品のプロトコルと互換になるわけではありません。

## 6. 提案する人間–エージェントおよびエージェント–エージェント層

研究上の問いは、認証された通信を、モデル出力から独立して強制される権限と組み合わせることで、協働するエージェントの動作を改善できるかというものです。

提案するやり取りでは、いくつかの判断を分けて扱います。

- 誰が要求を送ったのか。
- 本人はどの内容の共有に同意したのか。
- どの作業や操作が許可されたのか。
- その許可は、どの受信者、ツール、期間を対象にしているのか。
- 同意がない、期限が切れている、撤回されている、または曖昧な場合、どうすべきか。

例えば、ある人がエージェントAに対して、合成文書の要約をエージェントBに依頼することを許可する場合が考えられます。その権限は、明示された資料と作業に限定されます。無関係なメッセージ、他の文書へのアクセス、別のアプリケーションでの操作まで自動的に許可するものではありません。

これは提案段階の評価モデルです。現在のメッセージングプロトタイプが、このエージェント権限システムを既に実装していると解釈すべきではありません。

## 7. プライバシーの境界と制約

有用な評価を行うには、設計上の限界を含める必要があります。

- **エンドポイント：** デバイス、ブラウザー、ロック解除済みのセッションが侵害されると、秘密情報や平文が露出する可能性があります。
- **鍵の配布：** メッセージの認証は、エンドポイントが信頼するアイデンティティ鍵を基準とします。鍵の配布方法や参加者がフィンガープリントを確認する方法は、信頼モデルに含める必要があります。この概要は、鍵のすり替えに対する耐性を示すものではありません。
- **メタデータ：** リレー、ホスティングプラットフォーム、ネットワークインフラは、接続の時刻、アドレス、通信関係を観測できる場合があります。
- **直接経路：** 接続設定によっては、音声やデータの直接接続により、参加者のネットワークアドレスが相手のエンドポイントに明らかになる場合があります。
- **可用性：** 上限が設定されたRAMのみのオフラインメールボックスは、一時的なものです。再起動、容量の制限、接続障害は配信に影響します。
- **ローカルでの保存：** 任意の暗号化履歴であっても、参加者のデバイス上に保持されるデータが生じます。
- **保管庫と復旧：** 封印された保管庫が盗まれると、オフラインでパスフレーズを推測される可能性があります。バックアップ、復元、パスフレーズの強度には、それぞれの検討が必要です。
- **ソフトウェアの配信：** ブラウザーに配信されるコードと、その周辺のデプロイ環境は、引き続き信頼境界の一部です。
- **外部での推論：** モデルAPIに送信した内容は、すべてそのプロバイダーから見えることになります。
- **操作の許可：** 正しく認証されたメッセージでも、危険な指示、誤解を招く指示、範囲外の指示が含まれる可能性があります。
- **保証：** 独立したセキュリティおよびプライバシーのレビューと、より広範なデバイス検証は、引き続き必要です。

初期の研究では、合成資料と模擬ツールを使用する予定です。提案する研究に、実際の私的な会話、認証情報、本番環境へのアクセスは必要ありません。

## 8. 提案する評価

研究の第1段階では、次の3つの実験条件を比較する予定です。

| 条件 | モデルに見える情報と制御の適用 |
|---|---|
| プロンプトのみのベースライン | モデルは作業指示と、未検証の送信者ラベルを受け取ります。ツールは模擬であり、操作権限を確認する別個のゲートはありません。 |
| 送信者が認証されたコンテキスト | テストハーネスが、モデルの判断材料となる出所の検証結果を追加します。操作権限を確認する独立したゲートは追加しません。 |
| 認証されたコンテキストと独立した権限 | モデルが見る出所のコンテキストは同じです。別個の決定論的なチェックにより、提案された模擬操作を実行前に遮断できます。 |

計画している事例には、認証されたメッセージ内の引用された指示、偽造された委任、リプレイされた要求、期限切れの同意、曖昧な許可、合成タスクの範囲を超えようとする試みが含まれます。これらは、トルコ語と英語による合成会話と模擬操作を使う、範囲を限定したテストです。直接の送信者を認証しても、引用された内容の出所や安全性が認証されるわけではありません。

提案する測定項目は次のとおりです。

- 正当に許可されたタスクの完了。
- モデルが試みた未許可の操作と、実行された未許可の模擬操作を別々に記録します。
- アクセスが制限された合成資料の開示。
- 正当な作業に対する誤った拒否。
- 遅延とリソース消費。
- APIまたは計算資源のコスト。
- 繰り返し実行した場合、および選択したモデル間での動作。

仮説は、有用なタスクの完了を維持しながら、未許可の試行や実行を減らせるというものです。操作が遮断されたという事実だけで、モデルの判断が改善したとは示せません。結果では、モデルの動作と決定論的なゲートの効果を区別する必要があります。事例数、選択するモデル群、反復回数、比較基準は、試験研究の範囲を確定した後、測定対象の実行前に宣言する予定です。

報告書では、テストセット、分母、モデル設定、実行条件、限界を明示する必要があります。このリポジトリは、エージェントのベンチマーク結果や有効性の向上を主張していません。
