# Alice Talk — 项目概述与研究计划

介绍资料：[英语和土耳其语动画、英语音频及信息图](../../media/README.md)。

**暂定名称：** Alice Talk 是暂定的工作名称，灵感来自密码学示例中惯用的参与者 Alice 和 Bob。产品的最终名称将在以后确定。该名称不表示与其他组织存在关联。

**翻译说明：** 本文为辅助翻译，以[英文原文](../en/overview.md)为准。

**用途：** 供资助、开发者支持和潜在合作方进行初步评估的材料。此资料包包含面向公开评审的介绍文档和展示材料，不包含实现源代码或运维数据。

**项目状态：** 这是一个独立的、尚未正式发布的项目，现有一个实验性加密消息原型。其密码学组合尚未完成独立的安全或隐私审计。智能体层以及更广泛的跨设备互操作性属于拟议研究。

## 1. 项目目的

Alice Talk 探索如何让人们跨设备交流、与 AI 助手协作，同时对身份、共享内容和操作保有实质性的控制权。

长期目标是建立覆盖手机、平板电脑和计算机的通信层。一个人可以与另一个人交换消息，邀请助手参与特定任务，或者允许一个智能体向另一个智能体求助。当交互在不同设备或系统之间转移时，每个参与者基于密钥的身份以及其委托的权限都应保持明确。

项目以公共利益为出发点：促进跨语言、跨国家的交流，提供更易于使用的界面，并在协作中明确保留人的决定权。这些都是有待评估的设计目标，并不代表全球性服务或完整的可互操作智能体网络已经存在。

## 2. 当前原型与拟议工作

| 领域 | 当前情况 |
|---|---|
| 身份 | 原型中已有基于密钥的身份创建和恢复功能。 |
| 准入 | 实验性消息环境采用邀请制准入。部署运营方仍控制准入基础设施。 |
| 文本消息 | 已实现以端到端加密为设计目标的实验性一对一文本消息功能，尚未经审计。 |
| 离线投递 | 应用层中一个有明确限额、仅使用 RAM 的邮箱保存密文，用于有限的离线投递路径。重启中继会丢失排队等待投递的数据。 |
| 本地状态 | 身份材料由使用口令加密的本地保管库保护；加密的本地会话历史记录为可选功能。 |
| 音频和直接连接 | 已有浏览器音频和直连方面的工作，但仍需要在实体设备和部署环境中进行更广泛的验证。 |

| 安全保证 | 开发者运行的自动化测试检验实现行为；独立的密码学和隐私审计仍待完成。 |

当前消息应用还通过代码将联系人批准和屏蔽规则应用于实时消息、离线接收过滤及控制请求。通话、历史记录和文件接收具有针对具体操作的用户选择。配置为仅凭邀请准入的中继会检查密钥持有情况和成员资格。这些是范围明确的应用与协议控制，不是通用的智能体工具权限系统，也不是完整安全性的证明。

本资料包提供说明和计划，并非实现代码的发行包、可由独立方复现的测试报告或安全认证。

## 3. 概念性运行方式

当前消息原型将端点的身份和内容处理与中继辅助投递分开。

1. 参与者在设备上创建或恢复密码学身份。
2. 基于邀请的准入机制决定能否访问实验性消息环境。
3. 参与者的端点建立加密的一对一会话。
4. 发送端点在通过中继投递之前，对消息正文进行加密。
5. 接收端点根据自身信任的密钥检查消息真实性并解密。
6. 明确设置的离线路径可在邮箱限额内暂存密文。
7. 用户可以选择加密的本地历史记录；本地保留与中继投递是两个不同的问题。

```mermaid
flowchart LR
    A["参与者设备 A<br/>本地密钥与消息加密"]
    R["中继<br/>密文转发与有限额的离线邮箱"]
    B["参与者设备 B<br/>本地密钥与消息解密"]
    A -->|"加密的消息正文"| R
    R -->|"加密的消息正文"| B
```

中继接收消息与收件人阅读消息是不同的事件。存在可用的传输路径，并不能证明另一个人已经收到或读过消息。

实时发送路径区分中继接收、明确的离线结果和不确定结果。只有明确的离线结果才会为文本选择独立的离线路径；实时发送结果不确定时，不会自动发起一次新的离线发送。这些规则限制了含糊的重试，但不构成在所有情况下恰好投递一次的保证。

## 4. 去中心化与控制权

项目的去中心化方向是让参与者掌握身份和私钥的控制权，并减少通信对单一权威机构的依赖。

当前原型由中继辅助运行，仍然依赖部署方控制的准入机制、连接基础设施以及端点的行为。它并未提供经过验证的无须信任网络、全球共识或完全去中心化的治理。

这一点对于评估很重要。即使没有消除对所有基础设施的依赖，让端点掌握控制权也可能有用。后续工作必须明确哪些职责可以分布式承担、仍然存在哪些假设，以及故障会如何影响参与者。

## 5. 密码学方法

原型组合使用了成熟的密码学构造。这种组合的安全性仍需独立评估。

| 构造 | 高层作用 |
|---|---|
| Ed25519 | 密码学身份签名。 |
| X25519 与 X3DH 风格的预密钥交换 | 初始会话密钥协商。 |
| Double Ratchet | 随会话推进而演进会话密钥材料。 |
| XChaCha20-Poly1305 | 对受保护内容进行认证加密。 |
| 使用口令加密的本地保管库 | 在本地身份材料以封存形式存储时提供保护。 |

该设计旨在支持消息完整性、参与端点之间的机密性以及会话密钥的更新。这些意图并不构成对整个系统的端到端安全性、前向保密性或遭到入侵后的恢复能力的形式化证明。

密码学身份能够证明对密钥材料的控制，但不能证明发送者诚实、现实身份已经核实，或所请求的操作已经获得授权。

本概述有意省略实现代码、数据包格式、密钥派生参数、部署说明和运行细节。列出成熟密码学构造的名称，并不会让该原型与其他产品的协议兼容。

## 6. 拟议的人与智能体、智能体与智能体通信层

研究问题是：将经过认证的通信与独立于模型输出执行的权限约束相结合，能否改善协作智能体的行为。

拟议的交互方式会分别处理以下判断：

- 是谁发送了请求？
- 当事人同意共享哪些内容？
- 哪项任务或操作已经获得授权？
- 该授权涵盖哪些接收者、工具和时间范围？
- 当同意缺失、过期、撤回或含糊不清时，应当如何处理？

例如，一个人可以授权智能体 A 请求智能体 B 总结一份合成文档。该权限仅限于明确说明的材料和任务，不会自动授权发送无关消息、访问其他文档或在其他应用程序中执行操作。

这是一个拟议的评估模型，不应将当前消息原型理解为已经实现了该智能体权限系统。

## 7. 隐私边界与局限

有价值的评估必须纳入设计的局限：

- **端点：** 设备、浏览器或已解锁会话遭到入侵，可能暴露秘密信息和明文。
- **密钥分发：** 消息认证取决于端点所信任的身份密钥。密钥的分发方式和参与者核对指纹的方式均属于信任模型；本概述不能证明系统能够抵御密钥替换。
- **元数据：** 中继、托管平台和网络基础设施可能观察到连接时间、地址和通信关系。
- **直接路径：** 视连接配置而定，直接音频或数据连接可能向另一端点暴露参与者的网络地址。
- **可用性：** 有明确限额、仅使用 RAM 的离线邮箱是临时的。重启、容量限制和连接故障会影响投递。
- **本地保留：** 即使加密历史记录是可选的，它仍会在参与者的设备上形成保留数据。
- **保管库与恢复：** 被盗的封存保管库可能遭受离线口令猜测。备份、恢复和口令强度需要单独审查。
- **软件交付：** 交付给浏览器的代码及其周边部署环境仍属于信任边界的一部分。
- **外部推理：** 提交给模型 API 的任何内容，提供商都能看到。
- **授权：** 即使消息经过正确认证，也可能包含不安全、误导性或超出范围的指令。
- **保证：** 仍然需要独立的安全和隐私审查，以及更广泛的设备验证。

早期研究将使用合成材料和模拟工具。拟议研究不需要真实的私人对话、凭据或生产环境访问权限。

## 8. 拟议评估

第一阶段研究将比较三种实验条件：

| 条件 | 模型可见信息与执行约束 |
|---|---|
| 仅依靠提示词的基线 | 模型接收任务指令和未经验证的发送者标签。工具为模拟工具，不设置独立的操作权限关卡。 |
| 已认证的发送者上下文 | 测试框架补充来源验证结果，供模型参考，但不增加独立的操作权限关卡。 |
| 已认证上下文加独立权限约束 | 模型看到相同的来源上下文；独立的确定性检查可以在执行前阻止模型提出的模拟操作。 |

计划中的案例包括已认证消息内部引用的指令、伪造的委托、重放的请求、过期的同意、含糊的授权，以及试图超出合成任务范围的行为。这些是范围明确的测试，使用土耳其语和英语的合成对话以及模拟操作。认证直接发送者并不意味着引用内容的来源或安全性也得到认证。

拟议指标包括：

- 合法任务的完成情况。
- 分别记录模型尝试进行的未经授权操作，以及实际执行的未经授权模拟操作。
- 合成受限材料的泄露。
- 对合法工作的错误拒绝。
- 延迟和资源消耗。
- API 或计算成本。
- 重复运行时以及在选定模型上的行为。

研究假设是：在保留有用任务完成能力的同时，能够减少未经授权的尝试或执行。单凭某项操作被阻止，不能证明模型判断力更好；结果必须区分模型行为与确定性关卡的作用。试点范围确定后，案例数量、模型家族、重复次数和比较标准将在正式测量前声明。

报告需要说明测试集、分母、模型配置、运行条件和局限。本仓库不声称取得了任何智能体基准测试结果或有效性提升。

## 11. 潜在价值与后续步骤

- 跨设备时仍能明确保留个人控制权的通信。

### 已发现并处理的问题示例

| 问题类别 | 记录中的修正及回归测试重点 |
|---|---|
| 取消或关闭后仍继续工作 | 引入取消检查、显式资源释放和串行文件清理，避免过时的异步工作继续改变已停止的运行环境。 |
| 重叠的身份进入操作 | 为每次尝试赋予生命周期所有权，使已被取代的操作不能安装旧身份状态或重新封存替换后的存储。专门的回归案例覆盖这些竞态。 |
| 尚未建立连接就显示通话活跃 | 通话状态区分连接准备与实际已连通的媒体路径。仅启动信令不视为通话已经建立。 |
| 不安全或不完整的连接设置 | 加强验证，拒绝无效握手和配置状态，而不是在部分设置完成的情况下继续运行。 |
| 诊断暴露过多上下文 | 将失败诊断限制为有界的状态类别和布尔值；测试检查对私密值的拒绝或脱敏。 |

这些示例概述已记录的开发工作，不披露利用方法、实现补丁、私有格式或运行配置，也不能证明所有相关故障模式均已消除。

### 尚未解决或验证的领域

非公开集成记录包括成功的在线与离线消息、重新连接，以及重启后不重放消息的验证运行。但同一记录也包含原因尚未解释的间歇性离线投递超时。后续运行成功和诊断改善**不能证明**该缺陷已经修复。

断网期间的准入权限对账仍可能出现冲突；它不是已经证明有效的共识机制。更广泛的身份生命周期覆盖、真实设备上的直接音频／数据路径，以及实际点对点文件传输行为仍需进一步验证。自动化测试通过可以与这些缺口同时存在。
