# English video storyboard

Eight planned scenes for a factual grant-review explainer. Time ranges are editing targets, not verified timestamps from the generated video. The [English project brief](../docs/en/overview.md) is the factual reference.

## Scene 1 — A conversation, and a choice | 0:00–0:35

**Visual direction:** A person chooses one fictional document, one recipient and one task. Phone and computer appear as a conceptual sequence. Title card: “Temporary working name · Independent, pre-release project.”

**Evidence boundary:** Overview §§1, 6. Cross-device continuity is a direction under investigation; the name implies no organizational affiliation.

## Scene 2 — Choices enforced by the current messenger | 0:35–1:20

**Visual direction:** A solid-line panel labelled “Current prototype” shows the person approving or blocking a contact. Follow the choice to code-enforced checks on live messages, offline receipt and control requests. Show separate choice cards for calls, history and file acceptance. A dashed panel reads “Proposed general agent permissions.” No source code or internal names appear.

**Evidence boundary:** Overview §§2, 5–6. These are current, action-specific application and protocol controls. Show only the listed existing controls; broader capabilities are not claimed. No general agent-tool integration, security certification, production-readiness claim or interoperability claim.

## Scene 3 — Admission, delivery and careful retries | 1:20–2:05

**Visual direction:** Two generic devices and a relay. First show invitation/membership checks; then follow “Ciphertext.” Separate “Accepted by relay” from “Read by person.” A three-way outcome diagram sends only “Explicit offline result” to a temporary queue. “Uncertain” is labeled “No automatic fresh offline send.” A restart clears only the application mailbox.

**Evidence boundary:** Overview §§2–4, 7. Explain this as careful retry/duplicate handling, not universal exactly-once delivery. Admission infrastructure remains deployment-controlled. This is relay-assisted, not a demonstrated trustless network. RAM-only describes application behavior, not every operating-system or hosting-storage layer.

## Scene 4 — Progress, with an unresolved fault | 2:05–2:45

**Visual direction:** A small evidence ledger separates “Recorded corrections,” “Developer-run checks” and “Still unresolved.” Keep the offline-timeout row visibly open.

**Evidence boundary:** Overview §13. The first restricted test run failed its environment check; the permitted rerun passed without implementation changes. This is not a claim of a fresh remote-deployment test. Recorded corrections do not establish that every related failure mode was eliminated. Counts include comments, blanks and experimental code; they measure neither lifetime authorship nor security.

## Scene 5 — A message is not permission | 2:45–3:15

**Visual direction:** Under “Proposed research,” a model proposes an action. An external permission check sits between the proposal and a mocked tool. The model cannot rewrite the illustrated permission record.

**Evidence boundary:** Overview §§5–8. Authentication is relative to trusted identity keys; it establishes neither real-world identity nor the origin or safety of quoted content. The general agent tool-permission system is proposed; it is separate from the messenger's existing contact and action controls.

## Scene 6 — Test the distinction | 3:15–3:50

**Visual direction:** Three equal columns. Only the third includes an external gate. Show separate counters for “Attempted” and “Executed”; leave all result values blank and label them “Not yet measured.”

**Evidence boundary:** Overview §8. No improved agent benchmark result is claimed. Case counts, model families, repetitions and comparison criteria must be declared before measured runs.

## Scene 7 — Follow the boundaries | 3:50–4:20

**Visual direction:** A quiet boundary map around endpoint, relay, browser delivery and optional external model. Label exposures plainly; use no alarm effects or real addresses.

**Evidence boundary:** Overview §§4–5, 7, 13. Admission reconciliation can still collide; direct audio/data paths and actual peer-to-peer file-transfer behavior remain incompletely validated. Do not depict global consensus or completed device interoperability.

## Scene 8 — The next useful milestone | 4:20–4:55

**Visual direction:** Close on the person reviewing a plainly labelled request before choosing. Final card: “Experimental prototype · Proposed research · Independent review outstanding.” Use a neutral project-profile contact card only if requested.

**Evidence boundary:** Overview §§8–12. A smaller contribution means a smaller pilot; the schedule is a planning framework, not a delivery promise. The presentation does not accept offers, activate paid services or authorize charges.
